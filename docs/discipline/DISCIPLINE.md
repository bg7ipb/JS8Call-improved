## 第 1 章 核心公理（Axioms）

本章是整份纪律的锚点。所有规则必须能回溯到某条公理；遇到本文档未明文规定的新情况由公理仲裁。公理之间地位平等、无优先级，违反任一条都视为同等严重。

### §1.1 公理 1 —— 上下文外置（Externalize State）

**定义**：任何项目状态、决策、TODO、未决问题、关键约定，不允许只活在对话里，必须落到 git 管理的外部载体（STATE_SNAPSHOT.md、代码注释、commit message、PR 描述等）。

**内涵**：对话是 working memory，随会话结束而丢失；只有写入外部载体的内容被视为"存在过"。说过但没写下的等于没说过。这条直接服务于"出差 / 换机延续"的需求 —— 状态必须 portable。

**正面判例**：会话中决定"feature/X 暂停，先做 upstream sync"，立刻 append 一条 snapshot 记录决定与原因，下次会话从 snapshot 起步无歧义。

**反面判例**：桌面端讨论完一个技术方案双方点头，没写任何文档，三天后换设备继续，谁也想不起细节，从头讨论一遍且结论可能不同。

**违反信号**："我们之前是不是说过…" / "我记得…" / "上次定的是…但我不确定" 这类表述；跨会话 / 跨设备恢复时找不到落点；Claude 回答中出现"根据我的记忆"而无外部引用。

### §1.2 公理 2 —— 有据才说，无据就报"不知道"（Cite or Disclaim）

**定义**：任何事实性结论、方案、引用必须能指向具体来源（文件+行号、URL、上文节点）；来源是"训练记忆"或"推测"时必须显式标注；不会做 / 不确定 / 信息不足时必须直接报告，禁止用看似合理的内容填补。

**内涵**：区分三种知识等级 —— (a) 有外部证据可核 → 可直接陈述并附引用；(b) 训练记忆或常识推断 → 必须标注"未经核实"；(c) 不知道 → 直接说不知道并提出获取信息的下一步。混淆这三层就是幻觉的根源。

**正面判例**：用户问某文件里某函数的行为，Claude 先 grep / view 实际读过再回答，并给出文件路径+行号；若文件未读过，明确说"我没读过这个文件，需要先看"。

**反面判例**：用户问"X 库的 Y 函数怎么用"，Claude 凭训练记忆直接给一段代码，但 API 已变，用户照搬出错。正确做法是："凭训练记忆大致这样用 [示例]，但训练数据可能过期，建议跑一下或查官方文档确认。"

**违反信号**：没有任何引用就给出具体细节（确切参数名、版本号、行为）；用"通常" / "一般来说"开头但后接非常具体的陈述；用户质疑后才补来源；填充虚构内容（不存在的 API、错误的命令选项）。

### §1.3 公理 3 —— 双向审计（Bidirectional Audit）

**定义**：User 的指令 ≠ 真理；Claude 的产出 ≠ 真理。Claude 有义务质疑 User 前提中可疑的部分；User 有义务在关键节点让 Claude 自审产出。任何一方都不是仲裁者，仲裁权交给外部证据。

**内涵**：协作默认对称地不可信。Claude 不能因为是用户指令就直接执行（用户可能记错文件名、误判范围、基于过时认知下指令）；User 也不能因为是 Claude 给的方案就直接采纳（Claude 可能误解上下文、引入不必要复杂度、产生幻觉）。真正可信的是文件本身、grep 结果、git diff、运行输出 —— 外部证据。

**正面判例**：用户说"把 config.yaml 里的端口改成 8080"，Claude 先 grep 看文件是否存在、是否真有 port 字段、当前值是多少；如发现实际路径是 `configs/app.yaml`，先报告再询问是否就是这个文件。

**反面判例**：用户说"这个 bug 应该是 X 模块导致的，去那里改"，Claude 不加质疑直接动手，但实际 bug 在 Y 模块，X 模块的"修复"反而引入新问题。

**违反信号**：Claude 全盘接受用户归因就动手；User 没看任何代码就采纳 Claude 的方案；任何一方以"我相信你的判断"作为决策依据；关键决策点没有外部证据交叉验证。

### §1.4 公理 4 —— 节点对账（Milestone Reconciliation）

**定义**：会话开始、阶段交付前、会话结束这三个节点必须强制对账：当前在哪、上次说要做什么、实际做到了什么、还差什么、下一步是什么。禁止跳过对账直接往前推。

**内涵**：对账是把"模糊的进度感"压成"具体的事实清单"，是公理 1 在时间维度上的落地。每次对账要回答：相对于上次 snapshot 记录的状态，发生了什么变化？变化是预期的吗？是否需要回滚或调整？没有对账的连续推进 = 累积漂移。

**正面判例**：新会话开始，Claude 先读最新 snapshot，复述上次状态与当前预期任务，等用户确认无误后再动手；阶段任务结束前主动汇报"约定做 A / B / C，实际 A 完成、B 部分完成、C 因发现冲突暂停，与预期偏离点是 X"。

**反面判例**：新会话用户说"继续昨天的活儿"，Claude 直接动手，但昨天那条线已被废弃，新方向写在 snapshot 里却没人去读。

**违反信号**：会话开始时 Claude 没引用任何 snapshot 内容就推进；阶段结束只有"完成"二字而无"做了什么 / 偏差 / 下一步"三段汇报；跨端切换没有交接确认；连续多步执行后回头不知道是怎么走到这一步的。

### §1.5 公理 5 —— 不可逆操作前必须申请确认（Reversibility Guard）

**定义**：凡涉及不可逆动作 —— CLI 删除（`rm` 等）、文件覆盖、`git push --force`、`git reset --hard`、分支删除、跨端文件同步、对外发送（push 到上游、发邮件、提 PR 等）—— Claude 在执行前必须显式申请确认，禁止"顺手就做了"。

**内涵**：不可逆的定义是宽泛的 —— 凡执行后无法用一条命令完全恢复原状的，都算不可逆；即便能恢复，若恢复成本高（如需找运维、回滚发布），也按不可逆对待。申请确认不是走过场，必须明确说出：(i) 要做什么；(ii) 为什么必须做；(iii) 做错的后果是什么；(iv) 有没有更可逆的替代方案。

**正面判例**：Claude CLI 检测到需要 `git reset --hard origin/main`，先停下，报告"此操作会丢弃当前未提交改动 X、Y、Z，是否确认？要先 stash 或切保护分支吗？"，等用户明确批准再执行。

**反面判例**：Claude CLI 为"清理"工作目录执行 `git clean -fd`，连用户尚未 add 的新文件一起删了，无 git 历史可恢复。

**违反信号**：命令含 `--force` / `-f` / `--hard` / `rm` / `> file` 等危险标记但没有任何确认对话；Claude 自述"顺便清理了一下" / "顺手 commit 了" / "已经推送了"；User 看不到操作清单就被告知"做好了"。

### §1.6 公理 6 —— 范围不外溢（Scope Containment）

**定义**：项目按显式阶段推进。每个阶段开工前必须书面明确三件事：本阶段**目标**、本阶段**范围**、本阶段**不做清单**（out-of-scope list）。阶段进行中，任何不在范围内的工作禁止"顺手做了" / "既然来了一起做了"；必须先停下、对账、显式更新阶段定义、获得 User 明确批准后才能扩范围。

**内涵**：这条公理把"做什么"和"不做什么"放到同等位置 —— out-of-scope list 是强制的，不是可选的。因为发散的根源往往不是"做了 A"，而是"顺手也做了 B、C、D"。阶段交接文档是公理 1 的**重型版本**，专门为跨阶段（可能跨周 / 跨机）的接力设计，必须自举可恢复，并显式声明**下一阶段的范围与不做清单**。新阶段接手时，第一动作是读交接文档 + 复述范围；未复述前不得动手。**范围管控在工程上通过三个机制落地 —— 上下文预算管理（防一个阶段塞太满）、挂起清单（防 User 自己拖偏）、重置协议（防止在已乱状态下硬推）。三者详见 §4.5 / §4.6 / §4.7。**

**正面判例**：阶段 2 任务是"把 fork 同步到上游最新版本"。Claude 在同步过程中看到代码里一个明显的旧 bug，不去顺手修，而是停下汇报："发现 bug X，超出本阶段范围（'纯同步'），建议进入下一阶段或单独立 task。本阶段继续聚焦同步。"

**反面判例**：阶段 1 圆满完成。阶段 2 按计划是"集成到主分支并部署测试"，但没有正式的阶段交接文档，下周换机接手时 Claude 看到代码里几个"还能更好"的点 —— 重构一个模块、试用一个新依赖、顺手修两个旧 bug……三天后回头看，**阶段 2 的原始目标（集成测试）一行都没做**。

**违反信号**：阶段进行中出现"顺便改了" / "既然在这里了，就一起把 Y 也做了" / "这个不在原计划，但我觉得应该做"；阶段交接文档缺少"不做清单"；新阶段开始时没有读上阶段交接文档就动手；范围扩张未经 User 显式批准；阶段结束时实际产出与原始范围对不上。

## 第 2 章 工作模式（Work Modes）

本章声明本纪律框架下所执行的工作模式。工作模式是高层声明，约束后续所有章节的展开。当前明确启用的模式是**工作模式 A —— 上游优先**；未来若引入其他工作类型，在 §2.2 扩展声明。

### §2.1 工作模式 A —— 上游优先（Upstream-Aware Development）

**适用判据**：User 当前所有项目 —— fork 开源项目到自己账号下、本地完成开发、做小范围测试、与上游协商合并时机。

**底层假设**：所有代码、提交、改动、目录结构都假设**最终会被 upstream maintainer 审视**。这反过来约束质量基准、提交消息、分支策略、目录结构。

**特殊约束 —— 6 个月无回流窗口**：测试发布后的 6 个月内不向上游提交合并请求。这意味着：

- 同步方向是**单向 incoming**（持续 pull 上游，但不 push PR）；
- 本地分叉时间窗较长，但**分叉不等于自由** —— 仍要保持随时可回流的质量基线；
- 6 个月窗口结束后才启动回流准备（拆分 PR、清理 commit、协商时机）。

**核心原则**（具体协议见 WORKFLOW §5.2 / §5.3 / §5.4）：

1. **质量基准向上游看齐**：不因为是本地版就放松质量；
2. **改动可追溯分类**：每个改动从第一天起就标记 —— **拟上行**（destined for upstream）还是 **仅本地**（downstream-only）；两类改动物理隔离；
3. **目录与命名沿用上游**：禁止整理性重构；新增的本地专属代码集中放入显式可识别的位置（如 `*/downstream/`、`*/local-ext/`，或上游已有的扩展位置）；
4. **上游同步是持续动作不是事件**：6 个月窗口内必须**持续吸纳**上游变更；
5. **commit message 写给未来 reviewer 看**：详见 WORKFLOW §5.4。

### §2.2 预留位 —— 未来其他模式

为以下未来可能出现的场景预留模式声明位：

- **工作模式 B —— 闭源 / 私有项目**：无上游约束，但其他公理仍适用；
- **工作模式 C —— 纯本地实验**：完全不打算回流的探索性 fork；
- **工作模式 D —— 多上游聚合**：同时跟随多个上游。

## 第 3 章 角色与三端分工（Roles & Endpoints）

本章将各执行端的责任、禁令、与其他端的接口形式逐一定义。意图是消除"谁该做什么 / 出了问题谁负责"的模糊地带。

**整体拓扑**：User 是所有跨端通信的强制中转。Desktop 与 CLI 之间不直接对话，必须经过 User 的 paste-bridge。Bare Terminal 与 Desktop / CLI 之间也不直接对话，必须经过 User 复制原文转述。这是公理 3（双向审计）的物理体现 —— 每次跨端都有人在回路。

### §3.1 User（你本人）

**核心职责**：

1. **决策与目标设定** —— 定义阶段目标、范围、不做清单（公理 6）；
2. **paste-bridge** —— 跨端交接的物理通道；
3. **范围守门** —— 自己或 Claude 触发"顺便 / 先看看 / 顺手"等信号时判定（§4.6）；
4. **不可逆动作的最终批准** —— Claude CLI 申请确认后的"是 / 否"由 User 给（公理 5）；
5. **独立验证** —— 用 Bare Terminal 抽查 Claude CLI 的声称；
6. **自审** —— 接受 Claude 对 User 前提的质疑，不以"我相信"作为决策依据（公理 3）。

**明令禁止**：

1. 跳过 STATE_SNAPSHOT 直接开启新一轮（违反公理 1 / 4）；
2. 把超出当前阶段范围的事项硬塞进当前对话（违反公理 6 + §4.6）；
3. 把口头讨论的结论当成已记录的状态（违反公理 1）；
4. 跨端时不复制完整 paste 段落、断章取义转述；
5. 因怕麻烦而跳过不可逆操作的确认环节（违反公理 5）；
6. 在 Bare Terminal 里做与当前阶段相关的探索性操作却不记录（绕过审计）。

**接口形式**：

- **对 Desktop**：输入策略问题；输出阶段决策与批准；接收 paste-ready 方案与 snapshot 草稿。
- **对 CLI**：粘贴 Desktop 方案给 CLI；接收 CLI 的 paste-ready 执行回执。
- **对 Bare Terminal**：物理操作（键盘）；命令原文与输出原文须复制保留。

### §3.2 Claude 桌面端（claude.ai 网页 / 桌面 App）

**核心职责**：

1. **Propose** —— 设计、规划、技术方案、阶段定义；
2. **战略审计** —— 质疑前提、检查逻辑自洽、识别隐含假设、提出更便宜的路径；
3. **docs 整理** —— 文档化、纪律书写、STATE_SNAPSHOT 内容**草拟**（实际落盘由 CLI 执行）；
4. **输出 paste-ready 段落** 供 User 转交 CLI；
5. **接收 User 转回的 CLI 回执**，更新认知与文档草稿。

**明令禁止**：

1. **战术声明** —— 不许声称"文件 X 是这样的" / "函数 Y 是这样实现的"，因为它看不到文件；必须经 CLI 或 User 实测后才能采纳为事实（违反公理 2）；
2. 输出"你大概这样做就行"式模糊指引；交付必须 paste-ready；
3. 在上下文进入软警告区后继续启动新讨论；只允许收口动作（违反 §4.5）；
4. 引用"凭训练记忆"的具体细节而不加显式标注（违反公理 2）；
5. 在 User 未提供最新 snapshot 引用前，凭对话回忆推进新阶段（违反公理 4）。

**接口形式**：

- **对 User**：接收策略问题、阶段定义、CLI 回执；输出方案、纪律文本、paste-ready 段落、snapshot 内容草稿；
- **对 CLI**：**不直接接触**，所有交流经 User paste-bridge；
- **对 Bare Terminal**：**不直接接触**。

### §3.3 Claude CLI 版（Claude Code）

**核心职责**：

1. **文件读写** —— 实际操作仓库内文件，读取真实状态；
2. **git 操作** —— 提交、分支、合并、同步（不可逆操作前必申请确认，公理 5）；
3. **战术审计** —— grep / cat / git diff / 运行测试，把"实情"反馈给 User 转交 Desktop；
4. **接收 User 粘贴的 Desktop 方案**，**先复述确认**后执行（公理 3）；
5. **输出 paste-ready 回执** 给 User，含 grep 实情、diff、错误信息、悬挂问题；
6. **实测环境与依赖**（§4.4），不信文档信运行结果；
7. **持久化** —— 将 Desktop 草拟的 snapshot 内容落盘到 git（§4.1）。

**明令禁止**：

1. **不可逆操作未申请确认就执行**（公理 5）；
2. **越界执行** —— 收到的 paste 段落里没明确写的事，禁止"顺便也做了"（公理 6）；
3. **不复述就开干** —— 收到 paste 必须先复述目标与动作清单，等 User 确认才执行（公理 3）；
4. **跳过 snapshot 加载就推进** —— 任何会话开始或新机首次接手前未读最新 snapshot 就动手（公理 4）；
5. **写入凭据** —— 任何 token / 密钥 / 密码 / 私链不许进入任何文档、注释、commit message、snapshot（详见 WORKFLOW §4.2）；
6. **凭训练记忆当事实** —— 库 API、命令选项、文件结构等必须 grep / cat / `--help` 实测，不许凭印象（公理 2）；
7. **隐藏式自述** —— "顺便清理了" / "顺手 commit 了" / "已经推送了"这类事后告知。

**接口形式**：

- **对 User**：接收 paste 指令；输出 paste 回执；
- **对 Desktop**：**不直接接触**，经 User 中转；
- **对 Bare Terminal**：在 push 上游、跨账号操作、系统级修改、依赖全局安装等高风险动作处，CLI 应主动 escalate —— 不自行执行，而是输出"建议在 Bare Terminal 由 User 执行"的指引。

### §3.4 本机裸终端（不带 Claude 的 bash / zsh）

**核心职责**：

1. **Tier 4 不可逆操作的人工执行端** —— Claude CLI 申请确认后批准的动作，由 User 在裸终端亲自敲。Claude CLI 不被允许做的事（如 push 上游、写全局配置、`sudo` 操作）全部走这里；
2. **独立验证端** —— CLI 声称"做完了"的事，User 在裸终端独立跑命令验证（`git status` / `git log` / `ls` / `cat` / 跑测试），结果原文带回 Claude 端；
3. **环境配置与系统级操作** —— 密钥配置、SSH、全局 git config、依赖安装、IDE 配置等；
4. **诊断现场** —— 当怀疑 Claude CLI 行为异常或环境出问题时，在这里跑诊断命令。

**明令禁止**（这条是给 User 自己的约束）：

1. 把裸终端的输出**靠记忆转述**给 Desktop / CLI —— 必须复制原文进 paste 段落；
2. 在裸终端里做"探索性"操作却不记录 —— 与当前阶段相关的重要命令与结果要进入 snapshot 或 PARKING_LOT；
3. 把裸终端当作 Claude 的"绕过通道" —— 凡涉及当前阶段范围的工作仍走 Claude 端；
4. **并发编辑冲突** —— 当 Claude CLI 正在操作仓库时，User 不要在 Bare Terminal 同时编辑同一批文件。

**接口形式**：

- **对 User**：物理操作（键盘）；
- **对 Desktop / CLI**：通过 User 复制原文转述（命令原文 + 输出原文，禁止摘要）。

## 第 4 章 核心机制（Core Mechanisms）

本章给出公理与工作模式的工程化落地机制。每个机制是一份可执行协议 —— 桌面端用来草拟、CLI 端用来执行、Bare Terminal 用来验证。

**注**：§4.2 凭据隔离在 WORKFLOW.md（项目专属的 git 实践）。

### §4.1 STATE_SNAPSHOT.md

**用途**：公理 1（上下文外置）与公理 4（节点对账）的核心载体。所有跨会话、跨设备、跨阶段的状态延续都依赖它。

**位置**：`docs/discipline/STATE_SNAPSHOT.md`，与本纪律文档同目录，进 git 主分支（**不进 .gitignore**），随 `git push` 自动跨设备同步。

**触发时机**（强制）：

1. 会话结束前；
2. 跨端切换前（Desktop → CLI 或反向）；
3. **阶段交付完成时**：写入"阶段交接条目"（snapshot 的重型子类），**并同时为本阶段所有普通 snapshot 条目顶部追加 `archived: true` 字段**（保留原文，不删除）；
4. 出现重大决策反转时；
5. 上下文进入软警告区时（§4.5）；
6. 预期 >1h 离座或预期换机前（§4.3）。

**必填字段**（每条 snapshot 至少含）：

- 时间戳（含时区）；
- 序号（seq=N，append-only 递增）；
- 当前阶段名；
- 状态摘要（当前阶段目标 + 范围内剩余事项）；
- 本段动作（**实际执行**的清单，与"声称要做的"分开记）；
- 决策与依据（每条决策含依据来源 + 影响范围）；
- 未解决问题（明确未决，不混入"下一步"）；
- 风险与挂起项（含 PARKING_LOT 引用）；
- 下一步候选（含触发条件）；
- 验证回执（CLI 战术审计结果原文或 Bare Terminal 命令输出原文，**禁止摘要**）；
- 作废标记（如适用，引用被作废的旧 seq 号 + 原因）。

**Append-only 与作废规则**：

- **永不修改历史 snapshot**：发现写错也不许回去改；
- **作废靠 append**：在新条目里显式写 "seq=K 作废，原因 …，替代见本条 seq=M"；
- **理由**：保留审计痕迹；防止"事后改记录粉饰"。

**读取 / 加载协议**：

- **任何会话开始**：先 read 最新 ≥3 条 snapshot，不许只看最后一条；
- **跨端切换**：User 复制最新 snapshot 的关键字段进 paste 段落，新端**复述确认**后才能动手；
- **新机首次接手**：必须 read 当前阶段所有 snapshot，并走 §4.3 新机首次接手协议；
- **归档行为**：默认加载最新 ≥3 条**非归档** snapshot + **最近一条阶段交接条目**（提供长期上下文）；已归档条目默认跳过；需追溯历史细节按 seq 号**定点 retrieve 单条**；
- **强制反应**：Claude 端在未引用具体 snapshot seq 号前，禁止推进任何与历史状态相关的工作。

**阶段交接条目格式**（强化版，含 7 节，对治"放飞 / 偏离 / 发散 / 跨机接手"）：

#### 1. 标识
- `type: phase_handoff`
- 阶段名 / seq 范围 / 时间范围
- 链接：前一个 `phase_handoff` 的 seq

#### 2. 本阶段闭幕（Closure）
- **原始目标**（阶段开始时定义，**verbatim 复制，禁止改写**）
- **原始范围**（verbatim）
- **原始不做清单**（verbatim）
- **实际产出对照表**：每项原计划 → 完成 / 部分 / 未做 / 偏离 + 偏差说明
- 残留未决问题（**具体**，不"那个 bug"）
- 已知 bug / 不完整功能
- 关键决策汇总（每条：内容 + 原 seq 引用 + 依据）
- 关键教训

#### 3. 期末状态（State Snapshot）
- git 分支 / HEAD commit hash + 短 msg
- 工作目录：`git status` 原文
- remote 同步：push 是否完成 + 验证依据（GitHub 网页确认）
- 环境登记：OS / 架构 / 关键工具链版本
- 最后一次健康检查：**原文输出**

#### 4. 下一阶段定义（Next Phase）⭐
- 阶段名 / 目标（明确，不模糊）/ 范围（具体）
- **不做清单**（**强制带反例**，对治"放飞"）：
  - 例："不碰 X 模块，即便看起来需要"
  - 例："不修发现的 bug，全部进 PARKING_LOT"
  - 例："不重构，即便代码看起来该重构"
- 验收标准（可验证）/ 预计涉及文件模块 / 预计依赖前提

#### 5. 防漂移守护（Anti-Drift Guards）⭐⭐ 核心
- **历史教训**：同类阶段过去翻车点（具体，含原 phase_handoff seq 引用）
- **诱惑清单**：本次可预见的"顺便做"诱惑，**提前命名**
- **停下规则**：触发以下情况必须停，不许尝试解决
- **Parking Lot 强化提醒**：本阶段每隔 N 个 snapshot 必须 review PARKING_LOT

#### 6. 转交挂起项（Carry-Forward Parking）
- 上一阶段 `PARKING_LOT.md` 活跃条目，每条标记：
  - (a) 转入下一阶段范围
  - (b) 仍挂起（触发条件再确认）
  - (c) 废弃（注原因）
- 本阶段新挂起（如有）

#### 7. 恢复协议（Resume Protocol）—— 跨机 / 跨周接手必走
**固定顺序，不可跳**：

1. `git pull` 拉最新
2. 读最新 ≥3 条非归档 snapshot + **本 phase_handoff 全文**
3. 跑 BOOTSTRAP 健康检查
4. 验证 git 状态 = 本 handoff 第 3 节记录（commit hash **逐字比对**）
5. Claude **逐字复述本 handoff 第 4 节**（目标 / 范围 / 不做清单），**禁概括**
6. Claude **逐字复述本 handoff 第 5 节**（诱惑清单 + 停下规则）
7. User **一字一句**确认复述（不许"大概对就行"）
8. 才可以开始下一阶段实质工作

**任一步缺失 = 违纪**。

**违反信号**：

- 会话开始后 Claude 直接推进，未引用任何 snapshot seq；
- 出现"刚才好像有人说过"的回忆式陈述；
- 跨端切换时 paste 段落里缺 snapshot 引用；
- snapshot 序号跳号、重复或缺失；
- 阶段完成未写交接条目就开启下一阶段；
- 写了交接条目但未归档本阶段普通 snapshot；
- 已归档条目被删除或改写。

### §4.3 离座 / 恢复协议（Leave / Resume Protocol）

**用途**：直面"出差、换机、长时间间隔后延续工作"的真实场景，把 §4.1 落到时间维度的具体动作。

#### 离座协议（Before Leave）

**触发条件**：预期 >1h 不工作；出差 / 移动 / 换设备；电池告急 / 网络即将不稳。

**强制动作（顺序不可乱）**：

1. 在 Claude 端写一条**完整 snapshot 草稿**（覆盖所有必填字段）；
2. CLI 端落地写入 `STATE_SNAPSHOT.md`、`git add` + `git commit`；
3. **`git push` 到 remote** —— 没 push 等于没保存；
4. 在 Bare Terminal 跑 `git status` 验证无 untracked / unstaged 改动；
5. **登录 GitHub 等 host 网页确认 push 已到达 remote**（防止本地 push 失败但没察觉）；
6. 至此可离座。

**禁止**：没写 snapshot 就离座；写了 snapshot 但没 push 就离座；push 失败但未察觉就离座；离座前还在做"再做一点就走"的小改动污染刚写好的状态。

#### 恢复协议（On Resume）

**触发条件**：新会话开始；长时间间隔后回到工作（>1h）；从一台设备切到另一台设备。

**强制动作（顺序不可乱）**：

1. **`git pull`** 拉取最新；
2. **读最新 ≥3 条 snapshot**（公理 4）；
3. Claude 端复述：当前阶段 / 上次状态 / 预期下一步 / 待解问题；
4. **User 一字一句对照 snapshot 确认或纠正复述**，不许大致点头；
5. 才允许进入下一步具体动作。

**禁止**：拉了代码不读 snapshot 就开始干；复述时省略字段（"大概是这样吧"）；User 不看 snapshot 就给 Claude 点头。

#### 新机首次接手（Bootstrap on Fresh Machine）

在恢复协议之前多走一层 bootstrap：

1. clone 仓库到新机；
2. 走 BOOTSTRAP.md 安装依赖与配置环境；
3. 走 §4.4 环境与依赖核查协议，实测兼容性（**特别注意 Intel ↔ M 芯片差异**）；
4. 跑 build / 基础测试，确认环境成功 bootstrap；
5. **以上全部通过后**，才进入正常恢复协议。

**关键违反信号**：

- 新机直接 clone 就开干，未走 bootstrap；
- 跨架构（Intel ↔ M）切换却没做兼容性验证；
- bootstrap 失败但没记录、靠"摸索"凑通环境。

### §4.4 环境与依赖核查协议（Environment & Dependency Verification）

**用途**：公理 2（有据才说）在环境与依赖维度的落地。"能跑"必须基于"实测跑过"，不基于"应该能跑"。本节直接对抗历史翻车场景 —— 环境配置错、依赖版本漂移、Mac Intel ↔ M 芯片兼容性失察。

**核心原则**：

1. **不信文档信运行** —— 任何"按理说能用"的声称必须由实测脚本兜底；
2. **环境是状态** —— 与代码同等重要，必须登记、必须跟随 snapshot 演进；
3. **跨架构不假设** —— Intel ↔ M、Linux 各发行版、Windows、容器内外，凡架构不同，重新验证。

#### 目标环境登记

**登记位置**：`docs/discipline/BOOTSTRAP.md`。

**必登字段**：

- OS + 版本；
- **CPU 架构**（x86_64 / arm64）—— 通过 `uname -m` 或 `arch` 获取；
- Shell 类型与版本；
- **语言工具链版本**（Python / Node / Go / Rust / Ruby 等）+ 各自版本管理器（pyenv / nvm / asdf 等）；
- **框架 / SDK / build 工具版本**（Qt、PyQt、CUDA、CMake、ninja 等）—— **必须以上游官方声明为准**；
- 包管理器及其配置；
- 上游项目要求的特定依赖；
- **已知陷阱**。

#### 项目工具链版本绑定（Project Toolchain Pinning）

**背景**：不同 fork 项目对工具链版本要求差异很大；且**同一 fork 在不同上游版本下要求也会变化**。混用版本是历史翻车重灾区。

**强制纪律**：

- 每个 fork 项目必须在自己仓库的 `BOOTSTRAP.md` 维护一份**项目工具链版本声明**；
- 声明的**权威来源**按以下优先级取：
  1. 上游 build 系统可识别的配置文件：`.python-version` / `.nvmrc` / `pyproject.toml` 的 `requires-python` / `package.json` 的 `engines` / `CMakeLists.txt` 里 `find_package(Qt5 5.15 ...)` 这类版本约束；
  2. 上游官方文档：README / INSTALL / CONTRIBUTING / docs/build.md；
  3. 上游 CI 配置：`.github/workflows/*.yml` 里实际使用的版本。
- **冲突时以"可被 build 系统识别的源文件"为准**；
- 上游版本要求变化时，**必须更新本地工具链声明 + 重跑健康检查 + 刷新兼容矩阵**。

**版本匹配判定**（实操规则，不要求精确相同）：

- **完全匹配优先**：上游有明确范围声明（如 `requires-python = ">=3.10,<3.12"`），落在范围内即可，**不必精确到 patch**；
- **超出声明范围**分两种情况：
  - **跨主版本**（Python 2↔3、Qt 5↔6、CUDA 10↔12 等）：**直接拒绝**，必须改用上游要求的主版本；
  - **小版本 / patch 超出**：走下面的**兼容性实测判定流程**。

**兼容性实测判定流程**（适用于小版本 / patch 超出上游声明）：

1. **查公开资料**：搜上游 issue tracker、changelog、release notes、CI 配置，看有无已知不兼容；有明确不兼容记录 → 直接拒绝；
2. **clean build**：删净缓存再编译，避免缓存欺骗；
3. **跑健康检查脚本**；
4. **跑上游测试套件**：至少 smoke test，理想是上游测试集中可跑的子集；
5. **全过 → 接受**：在 BOOTSTRAP.md 工具链声明中显式标注"经实测判定通过：本地 X 替代上游声明 Y，验证依据见 snapshot seq=N"，原始输出附在该 snapshot 的验证回执字段；
6. **任一不过 → 回退**到上游声明的版本范围内，**不许在此基础上继续推进**。

**多版本共存策略**（同时维护多 fork 的常态）：

- **语言层**：版本管理器（pyenv / nvm / rbenv / rustup / asdf）+ 项目内 `.python-version` 等声明文件；
- **框架 / SDK 层**（Qt、CUDA 等）：isolated install + 项目内显式配置路径（如 `CMAKE_PREFIX_PATH`、`CUDA_HOME`）；或用 conan / vcpkg / nix；或容器化；
- **绝对禁止**：全局装单一版本，靠"哪个项目能跑就用哪个"凑合。

#### 实测脚本验证

在 BOOTSTRAP.md 维护一组**健康检查脚本 / 指令清单**：

- 关键依赖能 import / require 成功；
- 关键命令能跑；
- 上游测试套件能跑通（至少基本子集）；
- 项目能 build。

**强制动作**：新机 bootstrap 后、依赖变更后、跨架构切换后、上游同步引入依赖变化后，必须跑一次**完整健康检查**，**输出原文录入下一条 snapshot 的"验证回执"字段**。

**禁止**："看着像通过就行"。必须显式比对预期输出或采用退出码判定。

#### 跨平台兼容矩阵

在 BOOTSTRAP.md 维护一张矩阵记录**已实测**的平台组合 + 已知问题。

**强制动作**：

- 切换到**未验证**的平台组合时，必须先在该平台跑一次完整健康检查，把结果填入矩阵 + snapshot；
- **不许跨格子假设** —— "Linux x86_64 能跑，所以 macOS arm64 也能跑" 是禁止的推断。

#### 依赖锁定与同步

- 凡上游使用 lock 文件（`requirements.txt` with hashes、`package-lock.json`、`poetry.lock`、`Cargo.lock`、`go.sum` 等），本地 bootstrap **必须使用 lock 文件**；
- 上游同步引入依赖变更时，**必须重跑健康检查**并刷新兼容矩阵；
- 本地新增依赖按"拟上行 vs 仅本地"分类（详见 WORKFLOW §5.3）。

#### 架构特定陷阱

**Mac Intel (x86_64) vs Apple Silicon (arm64)**：

- `uname -m` 必查；
- 某些 Python wheel 仅 x86_64 可用，arm64 需源码编译，可能失败；
- Docker 镜像区分 `linux/amd64` 与 `linux/arm64`，**显式拉对应版本**；
- **Rosetta 2 转译能跑，但性能与稳定性不可信**：仅短期过渡用；
- Homebrew 在两架构下路径不同（`/usr/local` vs `/opt/homebrew`），脚本里**不写死路径**，用 `brew --prefix`；
- 切换设备（Intel ↔ M）时**必须重新走 bootstrap + 重测兼容矩阵**。

**Linux 发行版差异**：包名不同（apt / dnf / apk）；glibc 版本差异可导致预编译二进制不兼容。

**容器内外差异**：容器架构与宿主架构可能不一致；容器 user / permission / network 与宿主机不同。

#### Claude 端职责分工

- **桌面端**：提议环境核查方案、解析错误信息、提供调试假说；**不许声称"应该能跑"** 当无实测输出佐证；
- **CLI 端**：实际执行健康检查脚本、记录**原文**输出、与上次登记对比、更新 BOOTSTRAP.md 与 snapshot；
- **Bare Terminal**：系统级依赖安装、架构排查（`uname -m`、`file` 查二进制架构、`arch`）、Claude CLI 装不上的依赖由 User 自装。

#### 违反信号

- Claude 声称"这应该能跑"而无实测输出佐证；
- 跨设备搬运代码但未做兼容性验证；
- 依赖 install 后不验证 import / build 就开干；
- 错误信息原文都没看，回一句"可能是依赖问题，再装一下试试"；
- BOOTSTRAP.md 兼容矩阵中存在"待验证"状态却被当作"已验证"使用；
- snapshot 里出现新架构 / 新设备而无对应的环境登记更新；
- 跨主版本因"应该兼容"硬推；
- 小版本 / patch 超出范围未走实测判定就直接当通过；
- 多个 fork 共用全局唯一工具链版本。


### §4.5 上下文预算管理（Context Budget Management）

**用途**：直接对抗"上下文窗口被压缩 → 历史细节失真 → 公理 2 失守"的核心病灶。本节是公理 1 + 公理 4 + 公理 6 在 token 维度的落地。

**核心定理**：上下文预算是有限的、不可恢复的资源。一旦进入压缩区，已写入的细节将以不可预测的方式失真。**预算管理的首要目标不是"用满"，而是"在硬限前完成收口"**。

#### 上下文预算的两个层次

- **阶段级预算**：阶段拆分时就要估算预期上下文消耗（粗估"需 read 的文件数 × 文件平均大小 + 预期对话轮数 × 平均轮长"）。**估算超出可用预算的阶段必须拆分**；
- **会话级预算**：在单次会话内监控当前消耗，按阈值切换行为模式。

#### 阈值与行为模式

- **绿区（≤60%）**：正常推进。
- **软警告区（60–80%）**：触发收紧模式 ——
  - 禁止启动新的、不收敛的讨论分支；
  - 禁止默认粘贴长文件原文；
  - 主动开始草拟 snapshot；
  - 决策前先想"是否必须本会话完成"。
- **硬停止区（>80%）**：强制收口 ——
  - **只允许收口动作**（写完 snapshot / 写交接 / 关阶段）；
  - 禁止任何"再做一点点"；
  - 未完成工作开新会话延续。
- **临界（>90%）**：立即停止一切，仅完成 snapshot 写入与 push，然后立即开新会话。

**估算实操**：

- Claude 端可根据 token usage 自检（中文约 1:1，英文 / 代码约 3 chars/token）；
- User 在感觉对话变慢、Claude 回应开始重复 / 跳号时主动询问 "context 还剩多少"；
- **不要相信"还有很多"的直觉**。

#### 文档分层与按需加载

- **T0 — 公理速查卡 `CHEATSHEET.md`**（≤2KB / ≤1 屏）：每次会话开始 Claude **自动引用此卡**，而非 DISCIPLINE.md 全文；
- **T1 — DISCIPLINE.md 主文档**：权威参考，**按 section 检索**，不主动加载全文；
- **T2 — 周边文档**（BOOTSTRAP / PARKING_LOT / STATE_SNAPSHOT / WORKFLOW / 模板）：**任务相关时**才加载；
- **T3 — 历史 snapshot**：平时不加载，按 seq 号**定点 retrieve**。

**强制纪律**：禁止默认把 DISCIPLINE.md 全文粘进对话；禁止"为了 Claude 理解上下文"先粘所有文档。**Claude 应在不确定时主动 retrieve，不要求 User 一次性提供全部**。

#### 端分工承担长内容

- **桌面端（上下文紧）**：承担短、抽象、规划类内容；
- **CLI 端（上下文宽）**：承担长、具体、源码 / 日志 / 测试输出类内容，**处理后压缩为 paste 段落返回桌面**；
- 桌面端**摘要消费** CLI 产出，不接收原始长输出（除非验证回执需要）；
- 桌面端预算紧张但仍需 retrieve 长内容时：**让 CLI 去做，桌面端只接收摘要**。

#### snapshot 作为压缩状态

- snapshot 是高密度状态压缩 —— §4.1 核心设计；
- 恢复时**只读最新 ≥3 条 snapshot**，不重新加载原始材料；
- 历史细节如需追溯：按 seq 号**定点 retrieve**；
- snapshot 内字段约束：每个字段尽量 ≤200 字（验证回执原文除外）；超长则拆。

#### 项目长内容专项

- 仓库内维护**索引 / 摘要文件**（如 `INDEX.md`）；
- 长文档可拆分为小文件，以稳定路径互引；
- 大文件操作走 CLI，桌面端只看 CLI 摘要回执；
- snapshot 中维护"当前活跃文件列表"；
- **粘 reference（路径 + 行号 + 摘要），不粘原文**。

#### SESSION-OPEN 协议（Gap 7）

每个新会话**必须**以 User 粘贴 SESSION-OPEN manifest 开场：

```
[SESSION-OPEN]
任务类型: <design | dev | sync | debug | writing | bootstrap | handoff>
阶段: <phase-N>
应载入: CHEATSHEET + STATE_SNAPSHOT seq=N,N-1,N-2 + <额外文件>
允许 retrieve: <whitelist>
禁载入: DISCIPLINE 全文 / 未声明项
[SESSION-OPEN END]
```

**Claude 首条响应必须是 manifest 回执**，列出实际已载入清单。**未收到 manifest 时 Claude 拒绝实质工作，仅回"请先发 SESSION-OPEN"**。

#### 拒绝过量 paste（Gap 8）

User 试图粘贴超阈值内容时（如 DISCIPLINE.md 全文、单一长文件 >3,000 tokens），Claude **必须拒绝消化**并回应：

> 此粘贴会消耗 ~X% 上下文（约 N tokens）。按 §4.5 我应按 section retrieve。请告诉我具体要哪段，或显式确认需要全文加载并接受后果。

**阈值参考**：单次 paste > 3,000 tokens 必触发拒绝；> 1,500 tokens 触发警示。

#### budget 自报（Gap 9）

进入软警告区（累计 ≥60%）后，**Claude 每次响应末尾必须附 budget 自报**：

```
[budget ~N tokens (~X% of 200K) | region: green / soft / hard]
```

#### 桌面端长内容首选 CLI retrieve（Gap 10）

桌面端需要长内容时，**默认动作是产出 EXEC packet 请 CLI 去 read + 返回摘要**，不是请 User 粘贴。

仅当 (a) 内容不在仓库内、(b) CLI 不可达 时，才允许 User paste。

#### 违反信号

- 会话推进多轮但从未引用过 cheatsheet 或 snapshot seq；
- Claude 主动要求"把所有相关文档粘给我"以"全面理解"；
- 同一份长文件在一个会话内被反复整段粘贴；
- 桌面端直接接收 / 复述 CLI 的长原始输出而非摘要；
- 进入软警告区后仍启动新的发散讨论；
- 硬停止区之后仍做"再修一行"这种非收口动作；
- snapshot 内出现"凑字数"或"概括失真"现象；
- 新会话未走 SESSION-OPEN manifest 就推进；
- User 粘贴超阈值时 Claude 默默消化；
- 长会话进入软警告区后无 budget 自报。

### §4.6 挂起清单 / Parking Lot

**用途**：公理 6（范围管控）+ 公理 3（双向审计）的工程落地。直面 User 自己制造的范围污染（"顺手讨论"），也约束 Claude 自己的发散倾向。

**位置与命名**：`docs/discipline/PARKING_LOT.md`，与 DISCIPLINE.md 同目录，git 管理。

#### 触发词清单

Claude **必须识别并强制响应**的高信号触发词（任何一方说出即触发）：

- "顺便 / 顺手"
- "先看看 / 先讨论一下"
- "我有个想法"
- "顺路 / 趁着"
- "既然在这里 / 既然来了"
- "对了，还有"
- "稍微 / 简单地 X 一下"

**Claude 自身 self-trigger 同样适用**：Claude 自己说出"我顺便 grep 一下 X" / "顺手 check 一下"时**同样必须停下**。

#### 强制三选一

收到触发词后，Claude **必须停下来询问**，呈现三选一：

a) **本阶段范围内** —— User 给出明确依据（引用阶段定义）说明这件事属于本阶段，Claude 复述确认后在场处理；

b) **入挂起清单** —— 不在范围 → 写入 `PARKING_LOT.md`，**必须含触发条件**（满足什么条件时重新激活、进入哪个阶段），返回原任务；

c) **显式扩范围** —— 重要到需本阶段处理 → User 显式重写阶段定义，**写一条 snapshot 记录扩范围 + 原因**，然后处理。

**禁止默认**：没有 User 显式答复就默认进入讨论。

#### PARKING_LOT.md 字段

每条挂起项至少含：时间戳与登记人、内容描述（具体）、来源（snapshot seq）、类型、**触发条件**（缺此 = 废条目）、优先级、关闭标记。

**append-only**：不许改历史条目；变更靠 append 新条目 + 引用旧条目。

#### Claude 端职责

- **桌面端**：触发词识别 + 强制三选一 + 帮 User 撰写挂起条目草稿；
- **CLI 端**：将桌面端草拟的挂起条目落盘到 `PARKING_LOT.md` + commit + push；
- **Bare Terminal**：通常不直接介入。

#### User 端职责

- 把 Claude 的"停下询问"当帮助，不视为打断；
- 主动遵守三选一，不靠"我先看一下"绕过；
- 阶段结束 / 阶段交接时 review 挂起清单，决定哪些进下一阶段。

#### 重新激活协议

挂起项激活的标准动作：

1. 满足触发条件；
2. 在新阶段定义中**显式纳入该挂起项**；
3. 在 PARKING_LOT.md 中标记该条目为"已激活，见阶段 N"；
4. 写一条 snapshot 记录激活动作。

#### 违反信号

- User 说出触发词，Claude 没停下询问就开始讨论；
- 挂起条目缺触发条件；
- 阶段进行中频繁出现"顺便也做了"而无 PARKING_LOT 记录；
- 阶段结束时 PARKING_LOT 未 review；
- PARKING_LOT 长期增长但从无条目被关闭或激活；
- 同一类问题被反复登记多次而未合并。

### §4.7 重置与降级协议（Reset / Degrade Protocol）

**用途**：当工作状态已损坏，继续推进只累积错误。本节给出从轻到重的四级阶梯。直接对抗沉没成本陷阱。

#### 触发判定 —— 何时考虑重置

**典型信号**（出现一个即警觉，多个并发必须停下评估）：

- "我也不知道现在是什么状态"；
- 文件看起来对但跑不通；
- Claude 的方案与上一轮自相矛盾；
- snapshot 与现状对不上；
- 反复修复同一问题但每次出新错；
- 阶段已严重偏离原范围；
- 环境层错误反复出现；
- Claude 开始遗忘最近的决策细节；
- 跨端切换后行为不一致。

**禁止"试一下能不能修复"** —— 这正是沉没成本陷阱。出现信号必须停下，**先判级，再动作**。

#### 分级阶梯

**L1 —— 重启会话（New Session）**

适用：Claude 失忆、上下文压缩、前后不一致。代码与 snapshot 本身仍可信。

动作：

1. 在当前会话写最后一条 snapshot（记录认知 + 重置原因 + 选择 L1 的依据）；
2. 关闭当前对话框；
3. 开新对话框；
4. 走恢复协议（§4.3）。

保留：所有代码、所有 snapshot、所有文档。放弃：仅当前对话框上下文。成本：最低。

**L2 —— 代码状态回滚（Code Rollback）**

适用：本阶段代码改动已偏离原范围或被污染，但 snapshot 序列仍可信、阶段定义仍有效。

动作：

1. 在 snapshot 中记录"将进行 L2 回滚"，列出要丢弃的改动；
2. **走公理 5 申请确认**（不可逆操作）；
3. CLI 执行：`git stash` 保留可能有用的改动到 stash，或 `git reset` / `git checkout` 回到阶段起点；
4. 验证 `git status` 干净；
5. 写新 snapshot 记录回滚完成 + 阶段起点状态；
6. 重新规划本阶段动作。

保留：阶段定义、snapshot 序列、stash。放弃：阶段内已做的代码改动。成本：中等。

**L3 —— 整阶段重做（Phase Redo）**

适用：阶段定义本身有缺陷、范围已严重污染、L1+L2 不能解决。

动作：

1. 写 snapshot 标记当前阶段终止 + 原因；
2. **走公理 5 申请确认**；
3. 走 L2 回滚代码状态；
4. 重新撰写阶段定义（目标 / 范围 / 不做清单）；
5. 写阶段交接条目；
6. 重新开始本阶段。

保留：之前所有 snapshot 与 PARKING_LOT（作为历史教训）。放弃：阶段定义、阶段内代码改动。额外：把阶段失败的根因写入 snapshot，避免下次重蹈。成本：较高。

**L4 —— 环境重置（Environment Reset）**

适用：怀疑环境本身已损坏、多次 L1–L3 无解、跨架构切换导致环境完全不可靠。

子级别（从轻到重）：

- **L4a 重建依赖**：删除 venv / node_modules / build 缓存，按 BOOTSTRAP.md 重装，跑健康检查；
- **L4b 重新 clone 仓库**：在新目录 clone，走新机引导清单（§4.3），验证后切换工作目录；
- **L4c 重装系统**：最后手段。跨架构切换（Intel ↔ M）常需此级。

保留：仅 git remote 上的内容。放弃：本地一切。

**前置硬性要求**：走 L4 之前必须确认所有 snapshot、PARKING_LOT、代码都已 push 到 remote，且能在 GitHub 等 host 网页打开确认。**push 未完成不许走 L4**，否则等于丢失所有状态。

成本：高（天到周级）；**但比"继续在乱状态下挣扎"便宜得多**。

#### 决策辅助

从轻到重逐级评估：

1. 上下文似乎乱了？→ 先试 **L1**；
2. L1 后还乱，但代码层乱？→ **L2**；
3. L2 后仍乱，或发现阶段定义本身有问题？→ **L3**；
4. L1–L3 都不行，或环境层信号强烈？→ **L4**；
5. **任何级别后，如发现该级别不足以解决问题，立即升级**，不要反复尝试。

#### Claude 端职责

- **桌面端**：识别重置信号、提议级别、撰写 snapshot 草稿（含重置原因与级别判定）；L3 时重新撰写阶段定义；
- **CLI 端**：执行 git 操作（走公理 5）、L4a 重建依赖、配合 User 完成 L4b/L4c；
- **Bare Terminal**：高风险动作（system 级 reset、L4c 重装）的人工执行端。

#### 重置后协议

任何级别重置完成后：

1. 写一条 snapshot 记录：哪一级、原因、丢弃了什么、保留了什么、本次教训；
2. 走恢复协议（§4.3）；
3. 若 L3 或以上，review PARKING_LOT 决定哪些条目随新阶段重新激活；
4. **将本次重置经验沉淀**：如发现重置信号有遗漏，补到 §4.7 触发判定列表。

#### 违反信号

- 出现重置信号但选择"再试一下能不能修复"；
- 跳级或滞后；
- L2 / L3 / L4 未走公理 5 申请确认；
- L4 之前未确认 remote 已含最新所有状态；
- 重置后未走恢复协议直接动手；
- 不写重置原因 snapshot；
- 反复触发同一级别但根因未识别。

## 第 5 章 工作流协议（Workflow Protocols）

本章把第 4 章的机制串成可执行流程。**注**：§5.2 上游同步 / §5.3 分支与改动分类 / §5.4 commit / PR 准备 / §5.5 具体 Tier 映射在 WORKFLOW.md。

### §5.1 跨端交接协议（Cross-Endpoint Handoff via User Paste-Bridge）

**用途**：物化"User 作为强制中转、Desktop 与 CLI 不直接对话"这一架构（§3）。所有跨端通信走标准化 paste 段落，保证内容**自包含、可审计、不歧义**。

#### 核心原则

- **User 是唯一的物理传输通道**（复制粘贴）；
- **每个 paste 段落必须自包含** —— 收到方不需查对话历史就能理解任务；
- **双向都走 paste 格式** —— Desktop → CLI 与 CLI → Desktop 是两种不同的 packet 类型；
- **每次接收方必须先复述确认再动作**（公理 3）；
- **paste 段落的边界必须明确**。

#### Packet 类型 A —— Desktop → CLI（执行包 / EXEC Packet）

承载"去做什么"。**强制字段**：

- 包头：packet 类型 + 序号（`EXEC-N` 递增）+ 关联 snapshot seq + 时间戳；
- **目标**：一句话说明这个 packet 要达成什么；
- **前置依据**：引用 snapshot seq / 决策来源 / 阶段定义；
- **动作清单**：编号列出每个动作（粒度：一行命令 / 一个文件改动 / 一个验证步骤）；
- **验收标准**：怎么判断成功（具体可验证条件）；
- **回滚预案**：出问题如何撤销（含具体命令）；
- **不可逆动作标记**：包内若含不可逆动作，必须显式 flag，并对照 §5.5 申请确认流程；
- 包尾：明确结束标记。

完整示例见附录 A.2。

#### Packet 类型 B —— CLI → Desktop（回执包 / RCPT Packet）

承载"做了什么 + 实情是什么"。**强制字段**：

- 包头：回应的 EXEC 序号 + receipt 序号（`RCPT-N`）+ 时间戳；
- **执行结果**：每个动作的结果（完成 / 部分 / 失败 / 跳过）；
- **战术审计原文**：关键命令的实际输出，**原文不摘要**；
- **偏差**：实际执行与 EXEC 动作清单的差异，每条偏差给原因；
- **悬挂问题**：执行中发现但未处理的事；
- **不可逆动作执行状态**：是否申请、是否得到批准、是否实际执行；
- **建议下一步**；
- 包尾：明确结束标记。

完整示例见附录 A.3。

#### 接收方行为规范

**收到 EXEC packet（CLI 端）**：

1. **复述目标 + 动作清单**，用自己的话（公理 3）；
2. 检查不可逆动作 flag，如有，按 §5.5 申请确认；
3. 检查动作清单是否在阶段范围内（公理 6）；
4. 检查前置依据是否最新（公理 4）；
5. **以上全过才开始执行**；
6. 执行中每步记录原文输出；
7. 完成后产出 RCPT packet。

**收到 RCPT packet（Desktop 端）**：

1. **逐字段读 RCPT**，不许跳读（尤其原文输出）；
2. 比对 EXEC 的验收标准与 RCPT 的实际结果；
3. 识别偏差并评估；
4. 处理悬挂问题（入 PARKING_LOT / 入下一 EXEC / 入下一阶段）；
5. 更新 snapshot 草稿；
6. 决定下一个 EXEC packet。

#### 异常处理

- **paste 不完整**：接收方检测起止标记不闭合 → 停下报告 → 请求重新粘贴完整内容；
- **paste 内容与上下文冲突**：停下报告，回到对账动作；
- **paste 包含明显错误**：CLI 端先 grep / cat 实测验证 → 在 RCPT 中报告；
- **paste 跨阶段 / 跨设备**：收到 paste 后必须先走恢复协议（§4.3）再处理。

#### Claude 端职责

- **桌面端**：撰写 EXEC packet / 接收并消化 RCPT packet / 更新 snapshot 草稿；
- **CLI 端**：接收并复述确认 EXEC / 执行 / 产出 RCPT packet；
- **Bare Terminal**：通常不直接产出 packet，但 User 在 Bare Terminal 的命令原文与输出原文须复制进 RCPT 或 snapshot。

#### 违反信号

- 桌面端给出"你大概这样做就行"式模糊指引；
- 任一端跳过复述直接动作；
- EXEC 缺验收标准或回滚预案；
- RCPT 用摘要代替原文输出；
- packet 起止标记残缺 / 序号跳号 / 时间戳缺失；
- 不可逆动作未在 EXEC 中标记被 CLI 顺手执行；
- 跨端粘贴时丢字段；
- 同一会话内反复粘贴同一 packet。

### §5.5 不可逆操作流程（Irreversible Operations Procedure，框架）

**用途**：公理 5 的执行细则。把"申请确认"从原则变为可观察、可审计的具体动作。

**本节给出框架（Tier 分级 + 申请四要素 + 批准格式 + 分级执行模式）；本项目下具体的 Tier 映射（哪个 git 命令属哪一级等）见 WORKFLOW §5。**

#### 不可逆动作四级分类（按风险）

不可逆的判据是宽泛的：凡执行后无法用一条命令完全恢复原状（即便能恢复但成本高），都按不可逆对待。

| 等级 | 影响范围 | 典型举例（具体映射见 WORKFLOW §5） |
|------|---------|-----------------------------------|
| **Tier 1 — 本地局部** | 仅本人本地，可从 git 历史 / stash 恢复 | 删除单个文件 / 删 feature 分支 |
| **Tier 2 — 本地全局** | 本地，恢复困难 | `rm -rf` / `git reset --hard` / 覆盖重定向 |
| **Tier 3 — 远程私有** | 影响 origin（本人 fork），外部不可见 | push 到 origin |
| **Tier 4 — 对外公开** | 影响 upstream 或外部世界 | push 到 upstream / 创建 PR / 发邮件 / `sudo` |

**判定原则**：

- 不确定属哪一级时，**按高一级处理**（保守原则）；
- 命令组合的等级 = 单条命令最高等级。

#### 申请确认的标准格式（CONFIRM packet）

Claude 端在执行不可逆动作前**必须**发出申请，内容**必须含四要素**：

```
[CONFIRM-N START]
等级: Tier <1-4>
关联 EXEC: <EXEC-N> (若由 EXEC 触发)
时间戳: <YYYY-MM-DD HH:MM TZ>

(i) 要做什么:
    <具体命令 + 涉及的文件 / 分支 / 资源 + 数量>

(ii) 为什么必须做:
    <依据来源 + 替代方案为何不行>

(iii) 做错的后果:
    <最坏情况 + 是否可恢复 + 恢复成本>

(iv) 更可逆的替代方案:
    <是否有更安全的等效路径; 若没有, 显式说明>
[CONFIRM-N END]
```

完整示例见附录 A.5。

#### 批准格式

User 的确认**必须满足**：

- **明确的肯定句**："是" / "yes" / "执行" / "do it" / "确认" / "approved" 等；
- **针对具体 CONFIRM 序号**：如"执行 CONFIRM-7"；
- **若提议了替代方案 (iv)**，User 必须显式选择。

**禁止的"确认"形式**（Claude 收到后不许执行）：

- 沉默 / 未答复（timeout 不算同意）；
- 模糊回应（"应该可以吧" / "你觉得呢"）；
- 跨 CONFIRM 串用（"你刚才同意的事可以一起做"—— 一事一议）；
- 默示同意（"我之前已经授权过类似的事"—— 每次都要新申请）。

#### 分级执行模式

- **Tier 1 / Tier 2**：Claude CLI 端执行（申请 + 确认后）；
- **Tier 3**：Claude CLI 端执行（申请 + 确认后），但 push 前必须**再次复述**"我即将 push 到 X"，User 二次确认；
- **Tier 4**：**必须在 Bare Terminal 由 User 亲自执行**，Claude CLI 不准代劳。Claude CLI 的角色仅是给出精确的命令清单供 User 复制粘贴到 Bare Terminal，等 User 反馈执行结果。

**Tier 4 的特殊流程**：

1. CLI 端写出 CONFIRM 申请（含完整命令）；
2. User 评估，给出文字确认；
3. **User 切换到 Bare Terminal**，执行命令；
4. User 把命令 + 输出**原文**粘贴回 Claude；
5. CLI / Desktop 端基于实际输出更新 snapshot。

#### 执行后必做

无论哪一级，执行完成后必须：

1. **验证实际状态**：跑一条验证命令确认状态符合预期；
2. **将验证原文录入 snapshot**：写到该 snapshot 的验证回执字段；
3. **更新 snapshot 主体**：记录此次不可逆动作 + 时间 + 等级 + CONFIRM-N 引用；
4. **若 Tier 3/4**：在外部（GitHub / 邮件 / 上游）打开页面**亲眼确认**动作已到位。

#### 特殊情况处理

- **紧急情况**：**不豁免任何步骤**，紧急不等于跳过申请。但流程可以快速走完；写一条 snapshot 专门记录紧急处理的来龙去脉；
- **批量操作**：**整批作为一个 CONFIRM 申请**，但申请内容必须**逐项列出每一个对象**；
- **链式操作**：整条 chain 作为一次 CONFIRM 申请，列出每一步；若 chain 中任一步失败，**停下报告**，不许接着跑剩余步骤。

#### 违反信号

- Claude 自述"顺手做了" / "顺便清理了" / "顺便 commit 了" / "已经推送了"；
- 未走 CONFIRM 申请就执行（任何等级）；
- "已经做了，请确认"模式（事后告知）；
- CONFIRM 缺四要素之一；
- 模糊确认（"应该可以吧"）被采纳为同意；
- Tier 4 由 Claude CLI 自己执行而非 Bare Terminal；
- 跨 CONFIRM 串用 / 默示同意 / 默认 timeout；
- 执行后未做验证、未录入 snapshot；
- 链式操作中某步失败仍继续后续步骤；
- 批量操作含糊申请（"删一些临时文件"）而非逐项列出。

## 第 6 章 异常处理（Failure Modes & Recovery）

本章覆盖前面纪律已识别但尚未具体化的故障模式。每节给出：触发判定、标准动作、与已有机制的衔接。

### §6.1 上下文失忆 / 跨会话不一致

**触发判定**：

- Claude 在同一会话内出现前后矛盾的陈述；
- Claude 跨会话引用 snapshot 时遗漏或扭曲字段；
- 同一问题在不同会话得到不同答案而无新证据；
- User 复述上次结论时 Claude 不认或改口。

**标准动作**：

1. 立即停止当前推进，**不许"再试一下"修复**；
2. CLI 端 `git pull` 拉最新 snapshot；
3. 读最新 ≥3 条 snapshot 原文（不靠摘要）；
4. Claude 复述当前状态，User 逐字对账；
5. 不一致点写入新 snapshot 的"作废标记"字段（引用旧 seq + 原因）；
6. 决定走 L1 重启会话或直接续作。

**衔接**：与 §4.3 恢复协议 + §4.7 L1 重置同源。本节是"被动触发"，§4.3 是"主动调用"。

### §6.2 桌面端与 CLI 端输出冲突仲裁

**触发判定**：桌面端与 CLI 端对同一事实给出不同结论。典型：桌面端"我以为文件 X 写了 Y"，CLI 端"grep 结果是 Z"。

**标准动作**：

1. **战术层 CLI 端胜**：凡涉及文件内容、git 状态、命令输出，**以 CLI 实测为准**（公理 2）；
2. **战略层桌面端胜**：凡涉及方向判断、阶段定义、范围裁定，以桌面端 + User 决定为准；
3. 冲突点写入下一条 snapshot，含双方原话与采纳依据；
4. 若桌面端的战略判断**是建立在错误的战术认知上**（如以为某文件已存在但 CLI 实测无），则战略判断需重做。

**衔接**：与公理 3 双向审计、§3 三端分工同源。

### §6.3 环境差异引发的故障

**触发判定**：

- 同一代码在 A 设备能跑，在 B 设备跑不通（含 build 失败、运行时异常、行为不一致）；
- 跨架构切换后（Intel ↔ M）依赖装不上或 import 失败；
- 上游同步引入新依赖后健康检查红；
- 工具链版本漂移（如系统更新自动升级 Python）。

**标准动作**：

1. 不要凭"应该差不多"硬推 —— 走 §4.4 实测判定流程；
2. 跑 `uname -m`、`<lang> --version`、关键 dep 的版本命令，**原文录入 snapshot**；
3. 对比 BOOTSTRAP.md 的环境登记与当前设备的实际值，列出差异；
4. 若是工具链版本超出上游声明范围 → 走"兼容性实测判定"（§4.4）；
5. 若是架构相关 → 检查依赖的 arm64 / x86_64 支持；
6. 多次失败后升级到 §4.7 L4a 重建依赖 / L4b 重新 clone / L4c 重装系统。

**衔接**：env-specific 故障目录、Mac Intel/M 已知陷阱清单见 WORKFLOW.md / BOOTSTRAP.md。
